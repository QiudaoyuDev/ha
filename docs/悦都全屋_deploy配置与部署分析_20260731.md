## 2. 配置方法

### 2.1 `configuration.yaml` 装配（includes 模式）

```yaml
default_config:
frontend:    themes: !include_dir_merge_named themes   # 载入 themes/*.yaml
template:    !include templates/yuedu_ui.yaml          # 语义层
automation:  !include automations.yaml
script:      !include scripts.yaml
scene:       !include scenes.yaml
lovelace:    dashboards.yuedu-home → dashboards/dashboard-v2.yaml (mode: yaml)
homekit:     !include homekit.yaml
```

特点：**一切配置走 `!include` 拆分**，单一 `configuration.yaml` 只做装配，便于版本管理与局部修改——这是生产级 HA 配置的标准做法。

### 2.2 语义层（核心架构资产）

`templates/yuedu_ui.yaml` 把 `xiaomi_home` 原始实体（如 `sensor.xiaomi_cn_1193742494_s1_door_state_p_3_1021`）映射为：

- `sensor.yue_du_men_suo_zhan_shi_zhuang_tai`（门锁展示态）
- `sensor.yue_du_she_xiang_ji_zhan_shi_zhuang_tai`（摄像机）
- `sensor.yue_du_kong_diao_zhan_shi_zhuang_tai`（空调，带 `temperature` 属性）
- `sensor.yue_du_xun_huan_shan_zhan_shi_zhuang_tai`（循环扇）
- `sensor.yue_du_xi_yi_ji_zhan_shi_zhuang_tai`（洗衣机）
- `sensor.yue_du_quan_wu_zhan_shi_zhuang_tai`（全屋聚合，统计离线台数）

映射规则：原始 `unavailable/unknown/None` → `设备离线`；英文状态 → 中文（已上锁/未上锁、守护中/已关闭、运行中/已关闭、待机/洗涤中/任务完成）。**仪表盘与家人永不接触原始态或英文态**。

### 2.3 仪表盘 v4（UI 配置要点）

`dashboards/dashboard-v2.yaml` 的关键设计：

| 设计点 | 实现 | 现代 UI 规范对应 |
| --- | --- | --- |
| 布局引擎 | 原生 `type: sections` + `max_columns: 2` | 官方响应式栅格，移动端稳 |
| 设计令牌 | 每视图 `theme: 悦都暖石` | 主题变量集中管理 |
| 卡片语言统一 | 全站 `custom:mushroom-*`（title/template/chips/climate/fan/entity/select） | 视觉一致 |
| 就地控制 | `custom:bubble-card` `card_type: pop-up` + `hash: '#yuedu-...'` | 操作不离场（弹窗而非跳转） |
| 状态驱动 UI | `conditional` 卡：离线时收起可执行控件，仅显示"暂不可用" | 防错 + 容错 |
| 户型图 | `picture-elements` + 地图页 `icon` 触点 `navigate` 到 `#hash` | 空间入口 |
| 首页信息层级 | 全屋状态 → 空间 chips → 常用空间 → 快捷模式 → 预留空间 | 清晰的视觉优先级 |

### 2.4 主题：`themes/yuedu-warm.yaml`（设计令牌）

`悦都暖石` 是一套**固定白昼暖色主题**，集中定义：

- 主色 `#87593B`、强调色 `#167D7A`、背景 `#F1E7DA`、卡片 `#FFF9F1`；
- 卡片圆角 `20px`、轻阴影 `0 8px 24px rgba(96,67,40,.08)`、边框 `#DEC9B3`；
- 状态色：`success #167D7A` / `warning #B7791F` / `error #B54A41`；
- 背景径向渐变；**刻意不定义 dark mode**（避免系统深色把木色空间带入黑灰底）。

### 2.5 自动化 / 脚本 / HomeKit

- `scripts.yaml`：`yuedu_away_mode`（关风扇+开摄像机）、`yuedu_sleep_mode`（关风扇），**低风险、不写死空调温度、不碰门锁**。
- `automations.yaml`：`入户门未锁提醒`（模板触发，连续 5 分钟非"已上锁"）、`洗衣完成提醒`（状态含"完成/结束"）。
- `homekit.yaml`：桥接 4 个**安全实体**（空调/风扇/摄像机/洗衣机），门锁不暴露；`advertise_ip: 192.168.1.5`（见部署说明）。

## 3. 部署方式

### 3.1 HA 容器（Docker，host 网络）

`docker-compose.yml`：

```yaml
services:
  homeassistant:
    container_name: homeassistant-local
    image: ghcr.io/home-assistant/home-assistant:stable
    network_mode: host          # HomeKit mDNS/Bonjour 依赖 LAN 多播
    volumes: [./config:/config]
    environment: { TZ: Asia/Shanghai }
    restart: unless-stopped
```

`network_mode: host` 是为 HomeKit 多播发现所必需；配置通过 `./config:/config` 绑定挂载，便于在宿主机直接编辑 YAML。

### 3.2 ⭐ Windows 侧 HomeKit mDNS 旁路（关键部署细节）

**问题**：在 **Windows + Docker Desktop** 上，`host` 网络只是"四层（L4）直通"——HAP 的 TCP 监听（21063）能从 Windows 访问，但 **mDNS 多播公告仍被困在 Docker 的 Linux VM 内**，Apple 设备收不到配对广播。

**解决**：`scripts/` 在 Windows 宿主机上单独跑一个 Python 进程，把容器内的 HAP 记录**重新公告到物理 LAN**：

- `homekit_mdns_advertiser.py`：用 `docker exec` 在容器内跑一段 zeroconf `ServiceBrowser`，读取容器网络命名空间里**真实的 HAP mDNS 记录**（含每次重启都会变的 `sh` 配对哈希），再用宿主机 zeroconf 以 `cooperating_responders=True` 原样重播；每 30s 刷新，检测到哈希/属性变化即更新；只公告、不处理配对与控制。
- `install-homekit-mdns-task.ps1`：以**管理员**安装为 Windows **计划任务**（登录时启动、断电池允许、失败重试 3 次），并开放防火墙 `TCP 21063` + `UDP 5353`（仅 `Private` 配置文件）。
- `start-homekit-mdns-advertiser.ps1`：实际启动器。
- `requirements-homekit-mdns.txt`：锁定 `zeroconf==0.150.0`。

该旁路是**本部署在 Windows 上能用 HomeKit 的前提**，是整套方案中最具环境特性的部分。

### 3.3 集成源码 `source/ha_xiaomi_home/`

包含小米官方 `ha_xiaomi_home` 集成**完整源码**（含 `install.sh`、`test/`、`tools/`、`CLAUDE.md`、CHANGELOG）。用途应是本地安装/二次开发该集成（而非仅从 HACS 拉取），也便于在离线/内网环境部署。

### 3.4 外部配套（同属 `deploy/`，非本目录）

`deploy/micam/` 独立运行 Miloco + go2rtc，把小米摄像机桥接为内网 RTSP（`rtsp://127.0.0.1:8554/yuedu_living_camera`），再接入 HA Generic Camera。仅内网，不外暴露端口。

## 5. 风险与改进建议（配置 / 部署视角）

### 5.1 可复现性与版本锁定（P0）
- **锁定 HA 镜像 tag**（如 `:2026.7.x`）而非 `:stable`，避免某次升级破坏仪表盘/集成。
- **固定前端卡片版本**：`www/community` 仅含打包 JS、无 `manifest.json` 版本，建议在部署文档或 `requirements` 中记录所用 Mushroom/Bubble Card 版本，或改用 HACS 的版本钉选。
- **`source/ha_xiaomi_home` 与 `custom_components/xiaomi_home` 需同源**：源码与已装组件版本应一致，否则升级易错位。

### 5.2 部署脚本可移植性（P1）
- `install-homekit-mdns-task.ps1` 与 `start-homekit-mdns-advertiser.ps1` 中 **Python 路径硬编码为 `C:\Users\lzx10\AppData\Local\Python\pythoncore-3.14-64\python.exe`**，绑定到特定用户机器。建议改为从 `PATH` 解析 `python` 或读环境变量，提升可移植性。
- mDNS 旁路仅在 **Windows + Docker Desktop** 需要；若在 Linux 主机或 HAOS 上跑，`network_mode: host` 原生支持 mDNS，应条件化跳过该脚本（建议在 README 注明适用环境）。
- 防火墙规则限定 `Private` 配置文件，符合安全约束，建议保留并在文档强调"仅可信网络"。

### 5.3 配置健壮性（P1）
- `secrets.yaml` 与 `home-assistant_v2.db`/`home-assistant.log` 等运行产物存在于 `config/`，应在 `.gitignore` 中排除（`db`/`log`/`secrets` 不应入库）。
- 语义层 `yuedu_ui.yaml` 已把所有"原始实体读取"收敛到一处，是良好实践，建议**继续维持"仪表盘只引用 `sensor.yue_du_*`"的约定**，新增设备先建语义传感器。

### 5.4 UI 配置进一步演进（用户关注，基于已落地的 v4）
当前 v4 已实现此前建议的大部分 P0/P1（语义层、Sections、主题令牌、Pop-up、离线收起）。下一步可聚焦：

| 方向 | 建议 | 收益 |
| --- | --- | --- |
| 户型图可维护性 | 评估 `Floorplan Card`(SVG 实体映射) 替代 `picture-elements` 百分比坐标 | 新增设备改配置而非重调 `left/top`，热区更准 |
| 暗色模式决策 | 主题刻意无 dark mode；若未来要支持，需补一套 `lovelace-dark` 变量并验证 2.5D 底图 | 夜间护眼，但需重测底图 |
| 墙屏 / Kiosk | 引入 Kiosk Mode 或 ha-fusion 作为固定墙屏前端，复用现有语义层 | 客厅/玄关常驻地图 |
| 响应式断点 | `sections` 已支持；可针对平板设 `max_columns: 3/4` 的视图变体 | 多端一致 |
| AI 中枢（skill 方向） | 接入 Home Assistant MCP，使面板背后实例可被 AI Agent 程序化管控 | "人看+AI 管"双通道 |
| 设计令牌外溢 | 用 `card-mod` 把 `悦都暖石` 令牌下沉到弹窗/第三方卡细节 | 视觉进一步统一 |

## 6. 总结

`deploy/homeassistant` 是一套**生产级、Windows 友好、强调语义隔离与安全边界**的 HA 部署：

- **配置方法**成熟：`configuration.yaml` 纯 `!include` 装配，语义层统一收敛原始态，仪表盘 v4 采用原生 `sections` + Mushroom + Bubble Card Pop-up + `conditional` 离线收起。
- **部署方式**有鲜明环境特性：HA 用 Docker host 网络跑，HomeKit 在 Windows 上依赖一个 **Python/zeroconf 的 mDNS 重公告旁路**（核心部署细节），小米集成随源码附带便于内网安装，摄像机经独立 `micam` 桥接 RTSP。
- **主要改进点**集中在可复现性（锁版本）、部署脚本可移植性（去硬编码路径）、运行产物入库控制，以及 UI 侧的 Floorplan Card / Kiosk / HA MCP 等下一阶段演进。
